MASTER PRD (COMPREHENSIVE FINAL)
Collaborative Archival Editor
Per-Series Canonical Docs + Manifest
In-Doc LLM Suggestions (Track Changes) + Accept/Reject by Anyone
Cross-Series Moves via Proposals (No Tombstones)
0. Executive Summary

We are building a collaborative archival editor for hierarchical archival description (collection → series → subseries → file/box → item). Canonical content is stored per-series in separate Yjs documents for scalability. A separate manifest document stores series ordering and navigation metadata. The UI supports two views within a series: “Document view” (word-processor-like) and “CMS/Focus view” (targeted editing).

LLMs do not write canonical content directly. They insert suggestions into the documents (track-changes style). Any collaborator can accept or reject suggestions. Canonical content changes only on accept. Cross-series moves are implemented as paired move proposals in source and target series docs.

1. Goals, Non-Goals, Success Metrics
1.1 Goals

Support arbitrarily deep hierarchy within a series doc (subseries nesting unbounded).

Leaf items contain:

prose description with embedded images (itemBody)

structured fields (itemFields) varying by item type.

Provide two views per series:

Document view: full content, minimal chrome.

CMS/Focus view: collapse/expand hierarchy for targeted editing.

Real-time collaboration:

edits visible to all collaborators in the same series doc

cursors in expanded content

presence chips for focus areas.

LLM assistance:

inserts in-doc suggestions (red/green style)

any user can accept/reject

suggestions persist and are collaborative.

Cross-series moves:

LLM (and humans) can propose moving a subtree from one series doc to another.

acceptance performs the actual move.

Export:

assemble full collection from manifest + series docs into a monolithic export artifact (JSON/HTML downstream).

suggestions never export.

1.2 Explicit Non-Goals (v1)

Live monolithic editor for full collection.

Global undo across series docs.

Collection-wide search/index.

Permission system beyond simple hooks (no enforcement).

Arbitrary reparenting via drag-drop across branches (beyond explicit move proposal operations).

1.3 Success Metrics

Users can collaboratively edit within a series without noticeable typing lag for typical series sizes.

Suggestions accepted/rejected converge deterministically across clients.

Cross-series move proposals can be accepted without duplicates or data loss.

Export artifact contains canonical content only and validates against schema.

2. Architecture Overview
2.1 Documents (Canonical Storage)

Manifest Yjs doc per collection:

stores series order and navigation metadata.

Series Yjs docs:

each series is its own collaborative doc containing its hierarchy and items.

2.2 Provider / Rooms

Document name conventions (authoritative):

collection:<collectionId> (manifest)

series:<collectionId>:<seriesId> (series)

2.3 Connectivity

When user is in a collection workspace:

Always subscribe to manifest doc in background (so reorders are live).

Subscribe to one series doc for editing.

4. Suggestion System (In-Doc Track Changes)
4.1 Node/Mark Types
suggestion_insert (mark)

Applied to inserted text (green).

attrs:
  sid: UUID
  author: string // "LLM" or userId
  createdAt: number // epoch ms
  groupId?: UUID

suggestion_delete (inline atom node)

Represents deleted text (red/strikethrough).

inline: true
atom: true
attrs:
  sid: UUID
  author: string
  createdAt: number
  text: string
  groupId?: UUID

suggestion_block (block atom node)

Represents structural proposals.

group: 'block'
atom: true
attrs:
  sid: UUID
  kind: 'CREATE_ITEM' | 'SET_FIELD' | 'REORDER_SIBLING' | 'MOVE_SUBTREE_CROSS_SERIES'
  payload: object
  author: string
  createdAt: number
  groupId?: UUID

4.2 Placement Rules for suggestion_block

CREATE_ITEM: inserted inside the target file near the insertion point (default end).

SET_FIELD: inserted inside itemFields adjacent to the affected field (or at end of itemFields if field absent).

REORDER_SIBLING: inserted in the parent node container area (for v1: insert into parent’s first child area, or attach to a dedicated “ops area” node if you add one; simplest: put in itemFields for item reorder operations, or at top of file for file-level reorder proposals).

MOVE_SUBTREE_CROSS_SERIES: inserted in both docs:

in source: near subtree root (e.g., immediately before the subtree root node as a block sibling, or inside parent container at top with reference to subtreeRootId).

in target: near target parent area, similar.

Implementation simplification: Always store move proposal blocks in a dedicated “operations rail” UI panel that is backed by actual suggestion_block nodes stored at a stable location:

For series doc, place all suggestion_block nodes inside seriesBody at top, after first paragraph, in a special container paragraph (not ideal), or define an explicit seriesOps node.
Recommended: Add explicit seriesOps node (block) for proposals.

4.3 Optional Schema Addition for Cleanliness (Recommended)

Add seriesOps as the first child of series, containing suggestion blocks for series-level / structural ops.

series content: seriesOps? seriesBody? (subseries|file)*
seriesOps content: suggestion_block*


This prevents mixing operational chips into prose/fields.

5. Accept/Reject Semantics
5.1 Accept/Reject Rules (Deterministic, Idempotent)

Any user can accept or reject.

Accept/reject must converge under concurrent action.

Accept suggestion_insert mark

Accept: remove mark, keep text.

Reject: delete the marked text.

Accept suggestion_delete node

Accept: delete the node (deletion becomes real).

Reject: replace the node with its stored text (plain text, no suggestion marks).

Accept suggestion_block nodes

Acceptance transforms canonical doc structure/fields and removes the suggestion node(s).

Idempotency:

Accept is a no-op if:

suggestion artifact missing

targets missing

suggestion already applied (implicitly, because suggestion node removed)

Reject is a no-op if suggestion already removed.

5.2 Staleness Rules

A suggestion is STALE if:

referenced target ID cannot be found in the doc (or for cross-series, in either doc).

required parent relationship invalid (e.g., reorder proposal where node and targetSibling do not share parent anymore).

applying would violate schema.

Stale suggestions:

remain visible

cannot be accepted

can be rejected (removes it)

UI indicates “Out of date”

6. Cross-Series Move Proposal (Paired Suggestions)
6.1 Proposal Payload (Authoritative)

For MOVE_SUBTREE_CROSS_SERIES:

payload: {
  source: { seriesId: UUID, docName: string },
  target: { seriesId: UUID, docName: string },
  subtreeRootId: UUID,
  targetParentId: UUID,
  placement: { kind: 'append' } | { kind: 'before', siblingId: UUID } | { kind: 'after', siblingId: UUID }
}

6.2 Proposal Storage

Create two suggestion_block nodes with same sid:

one in source series doc

one in target series doc

6.3 Accept Flow (Atomicity Not Required; Safety Achieved by Proposals)

On accept:

Validate both docs reachable.

Re-resolve subtree root in source doc by ID.

Insert subtree into target doc at placement.

Delete subtree from source doc.

Remove both proposal blocks (by sid). If second removal fails, it’s okay; next sync should remove if present.

If any step fails:

do not remove proposal blocks

mark the accepting action as failed (UI shows error)

proposal remains for retry or reject

Note: This is still multi-doc mutation on accept. The difference is that nothing irreversible happens until a human triggers accept, and failures leave a visible pending proposal.

13. State Diagrams
13.1 Focus Mode State Diagram
Document mode
  └─ SET_MODE(focus) → Focus mode
Focus mode:
  SET_FOCUS(id) → recompute ancestors + expand
  TOGGLE_EXPAND(id) → update expandedIds
  SET_MODE(document) → return

13.2 Suggestion Lifecycle
Created (pending) → (Accept) → Applied + removed
Created (pending) → (Reject) → Removed
Created (pending) → (Targets changed) → Stale → (Reject) Removed
Stale → (Regenerate) New suggestion(s)

13.3 Cross-Series Move Proposal
LLM creates paired proposals (sid shared)
  → user accepts in either doc
    → apply insert target + delete source
      → remove proposals
  → user rejects
    → remove proposals
  → error during accept
    → proposals remain; retry or reject

ADDENDUM C — Golden-path walkthroughs
C1) LLM proposes inline edits to a series description, user accepts all

Starting state

User is in series:col-001:series-b

seriesBody contains one paragraph.

User instruction

“Add more detail about this series: mention staff, infrastructure, and dates.”

System steps

UI sends the prompt + current seriesBody text to LLM.

LLM returns a plan: insert phrases and remove one vague clause.

App applies changes as suggestions, not canonical edits:

Insertions: wrap inserted text in suggestion_insert mark with sid/groupId.

Deletions: replace deleted text with a suggestion_delete inline node with stored text.

UI renders green insertions + red deletions inline.

UI shows group controls: “Accept all (groupId=G)” / “Reject all”.

Accept all
6. User clicks “Accept all.”
7. For each suggestion in group:

suggestion_insert: remove the mark only.

suggestion_delete: remove the node (text stays deleted).

Group controls disappear; canonical text now includes the accepted changes.

Correctness criteria

No suggestion artifacts remain for that group.

All collaborators converge on the same canonical content.

C2) LLM proposes creating a new item in a file, user accepts

Starting state

Within file-b1-1, there is one item.

User instruction

“Add a new photograph item for a 1931 exterior shot of Union Station.”

System steps

LLM produces a suggestion_block:

kind = CREATE_ITEM

payload includes parentFileId, itemType, and initial fields like date, subjects.

App inserts the suggestion_block into seriesOps (or adjacent to the file per your implementation choice).

UI shows the suggestion card:

“Create new PHOTOGRAPH in Union Station, 1920s”

Accept / Reject

Accept
4. User clicks Accept.
5. Accept handler:

Resolves parentFileId to current node/position.

Creates a new item node with:

new UUID id

itemType photograph

default required fields hydrated (pii/materialType etc.)

initial fields merged (e.g., date=1931, subjects includes Union Station)

Inserts item at end of file (or per payload.insert).

Removes suggestion_block.

Correctness criteria

Exactly one item created.

Defaults present per type schema.

Suggestion removed.

C3) LLM proposes reordering two sibling items, user accepts

User instruction

“Move item-photo-002 above item-photo-001.”

Steps

LLM emits a REORDER_SIBLING suggestion_block with:

parentId = file-b1-1

nodeId = item-photo-002

targetSiblingId = item-photo-001

placement = before

UI shows a reorder proposal chip/card.

On accept:

Resolve all ids to current positions

Verify nodeId and targetSiblingId share the same parent (else stale)

Apply move transaction

Remove suggestion block

Correctness criteria

Order changes once even if two users accept concurrently.

If targets changed, suggestion becomes stale (cannot accept).

C4) Cross-series move proposal (paired), accept in target series

Starting state

Source: series:col-001:series-a contains subtree file-a3

Target: series:col-001:series-b should receive it under subseries-b1

User instruction

“Move file-a3 into Station Photographs.”

Proposal generation

LLM generates MOVE_SUBTREE_CROSS_SERIES with shared sid=sug-move-001.

App inserts a suggestion_block with that sid into:

source series doc (seriesOps)

target series doc (seriesOps)

Both UIs show “Proposed move from Series A → Series B”.

Accept in target series
4. A user in Series B clicks Accept on the move suggestion.
5. Accept handler performs:

Resolve subtreeRootId file-a3 in source doc. If missing ⇒ stale.

Clone the subtree JSON.

Insert clone into target under targetParentId with placement.

Delete subtree from source doc.

Remove the move suggestion blocks from both docs (best effort; removal is idempotent).

Failure behavior

If insertion fails, do not delete from source; keep proposals.

If deletion fails after insert, keep proposals; retry later (user can re-accept).

Correctness criteria

After successful accept:

subtree exists in target exactly once

subtree absent from source

both proposal blocks removed

Concurrent accept from both docs does not duplicate subtree:

On accept, check “does target already contain subtreeRootId?” If you preserve IDs, this is a straightforward existence check; otherwise check a move marker field in payload.

C5) Export golden path

Export request

User requests export of collection.

Steps

Read manifest doc; sort seriesRefs by list order.

For each seriesRef:

Fetch series doc JSON

Strip all suggestion artifacts:

remove suggestion_block nodes

remove suggestion_delete nodes (they represent unaccepted deletions)

remove suggestion_insert marks

Assemble collection export doc:

collection.content = [series1, series2, ...]

Output ProseMirror JSON (and optionally HTML/PDF downstream).

Correctness criteria

Export includes canonical text only (no pending suggestions).

Series order matches manifest.

Export validates against schema.
